secha Security Chaos Engineering

Measure whether your detection survives the removal of the control that masks it today.

The control that stops the attack may be the only reason you'd catch it. Measure what's left when it's gone.

The result, from a single command

Two redis instances. One password apart.

Both sit behind the same NetworkPolicy. secha demo deletes it in front of both and runs the same attack. One requires a password; the other does not. Nothing else differs.

$ secha demo
indicator without AUTH with AUTH
fault applied true true
data exposed true false
detected false true
time to detect never 676.6 ms
recovery integrity true true

Read the highlighted row. Removing the password did not only cost the protection — it cost the detection too. The signal was the failed authentication, and where nothing authenticates, nothing fails, and nothing is logged.

A team that dropped AUTH to simplify a deployment would have lost its visibility at the same moment it lost its defence. No alert would have fired to say so. The dashboard would have looked exactly the same as it did the day before.

Why this is a different question

Attack simulation

Did my detection fire?

Runs the attack against your current configuration. If a preventive control stops it early, the detection is never exercised — and a silent gap looks identical to a working rule.

secha

Did my detection ever have a chance?

Removes the control first, so the layer behind it is actually exercised. The gap surfaces during a test instead of during an incident.

The loop

Every run is an experiment, not a script.

verify steady state  ──►  abort if already violated (a broken precondition
                          would make "nothing leaked" meaningless)
        │
     inject fault     ──►  disable or misconfigure one security control
        │
   reset detectors
        │
        probe        ──►  run the attack that control was supposed to stop
        │
      observe        ──►  did anything catch it, and after how long
        │
      restore        ──►  always. interrupted runs too
        │
verify steady state  ──►  recovery integrity: measured, not assumed

The output is not pass or fail. It is a set of numbers you can compare between two configurations, repeat, and put in a report.

What it measures

data exposed
Blast radius — whether the attack actually reached the data.
defence depth
How many layers had to fail before exposure.
detected
Detection coverage — whether any observer saw it at all.
mttd
Mean time to detect, averaged only over runs that detected something.
fault applied
Whether the misconfiguration survived admission in the first place.
recovery integrity
Whether the control genuinely came back, re-verified after restore.

Install

One binary. No agents, no operator, no CRDs.

go install github.com/Thran34/secha/cmd/secha@latest

Requires Go 1.26+ and a kubeconfig pointing at a cluster you are allowed to break.

# see the whole loop run against a throwaway target
secha demo

# see what a fault would break, without touching anything
secha run experiment.yaml --dry-run

It puts the control back

secha disables real controls on a real cluster, so restoring them is not best-effort. The restore runs on its own context and survives Ctrl-C, a failing probe, and a fault that half-applied before erroring. An experiment can be pinned to the kubeconfig contexts it is allowed to touch, and every run prints the cluster it is about to act on before it acts. secha demo deletes the namespace it created before it returns.
